## 二、软件工程基础

### 2.1 软件工程概念

**软件工程**是将系统化、规范化、可量化的方法应用于软件的开发、运行和维护的工程学科。

软件工程的**三要素**：方法（How）、工具（Tool）、过程（Process）。

### 2.2 软件开发模型

主要软件开发模型对比：

| 模型 | 特点 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **瀑布模型** | 顺序执行，阶段清晰 | 文档完整，易管理 | 不适应需求变化，风险后置 | 需求明确、稳定的大型项目 |
| **原型模型** | 快速构建原型，迭代反馈 | 适应需求不明确 | 可能导致需求蔓延 | 需求不明确，用户参与度高 |
| **螺旋模型** | 迭代+风险分析 | 风险管理好 | 复杂，成本高 | 大型高风险项目 |
| **增量模型** | 分批交付，每次增加功能 | 早期可用，风险分散 | 需要良好架构设计 | 需要早期交付部分功能 |
| **迭代模型** | 多次迭代，每次完善 | 灵活，适应变化 | 需要持续用户参与 | 需求不稳定的项目 |
| **敏捷模型** | 小步快跑，快速响应 | 响应变化快，交付快 | 文档少，不适合大型项目 | 需求变化频繁，小团队 |

> 记忆要点：**螺旋模型**最大特点是**风险分析**，每次迭代都要进行风险评估，适合大型高风险项目。

### 2.3 统一过程（RUP）

**RUP（Rational Unified Process）**是一种迭代式软件开发过程框架，分为四个阶段：

| 阶段 | 目标 |
|------|------|
| **初始阶段** | 确定项目范围和可行性 |
| **细化阶段** | 分析需求，建立架构基线 |
| **构建阶段** | 开发和测试软件 |
| **移交阶段** | 部署和交付给用户 |

> 记忆口诀：**初细构移**（初始→细化→构建→移交）

### 2.4 敏捷开发

**敏捷宣言四大价值观**：
- 个体和互动 > 过程和工具
- 可工作的软件 > 详尽的文档
- 客户合作 > 合同谈判
- 响应变化 > 遵循计划

**Scrum 框架**（最常考的敏捷方法）：

| 角色/事件/工件 | 说明 |
|-------------|------|
| **产品负责人（PO）** | 定义产品需求，维护产品待办列表 |
| **Scrum Master** | 移除障碍，保障团队遵循Scrum流程 |
| **开发团队** | 自组织，完成Sprint目标 |
| **Sprint** | 固定时间盒（1-4周），每个Sprint交付可工作软件 |
| **产品待办列表** | 所有需求的优先级列表（PO维护） |
| **Sprint待办列表** | 本Sprint要完成的任务列表 |
| **每日站会** | 15分钟，同步进展，识别障碍 |

## 三、需求工程

### 3.1 需求的分类

| 需求类型 | 说明 | 示例 |
|---------|------|------|
| **功能需求** | 系统应该做什么 | 用户登录、订单查询 |
| **非功能需求** | 系统应该怎么做 | 响应时间<2秒、99.9%可用性 |
| **约束需求** | 开发和运行的限制条件 | 必须使用Java开发、预算100万 |

### 3.2 需求开发过程

需求开发的四个步骤：

| 步骤 | 主要工作 |
|------|---------|
| **需求获取** | 访谈、问卷、观察、原型、头脑风暴 |
| **需求分析** | 建立需求模型，识别冲突，确定优先级 |
| **需求规格说明** | 编写软件需求规格说明书（SRS） |
| **需求验证** | 评审需求，确认需求正确、完整、一致 |

> 记忆口诀：**获分说验**（获取→分析→说明→验证）

### 3.3 需求分析方法

| 方法 | 说明 |
|------|------|
| **结构化分析（SA）** | 以数据流图（DFD）为核心，自顶向下分解 |
| **面向对象分析（OOA）** | 以用例图、类图为核心，识别对象和关系 |
| **用例建模** | 用用例图描述系统功能和用户交互 |

**数据流图（DFD）**的四个基本元素：
- **外部实体**：数据的来源或去向（矩形）
- **处理**：对数据的加工转换（圆形/椭圆）
- **数据流**：数据的流动方向（箭头）
- **数据存储**：数据的存储位置（双横线）

## 四、软件测试

### 4.1 测试的基本原则

- 测试只能证明软件**有缺陷**，不能证明软件**没有缺陷**
- 穷举测试是不可能的
- 测试应该**尽早**介入（越早发现缺陷，修复成本越低）
- 缺陷具有**群集性**（80%的缺陷集中在20%的模块）
- 杀虫剂悖论：同样的测试用例反复使用，发现缺陷的能力会下降

### 4.2 测试类型

| 测试类型 | 说明 |
|---------|------|
| **功能测试** | 验证功能是否符合需求（黑盒） |
| **性能测试** | 验证系统在负载下的表现（响应时间、吞吐量） |
| **压力测试** | 超出正常负载，测试系统极限 |
| **回归测试** | 修改后重新测试，确保未引入新缺陷 |
| **冒烟测试** | 快速验证核心功能是否可用（上线前的基本检查） |
| **用户验收测试（UAT）** | 用户验证系统是否满足业务需求 |

### 4.3 测试方法

| 方法 | 说明 | 技术 |
|------|------|------|
| **黑盒测试** | 只关注输入输出，不看代码 | 等价类划分、边界值分析、因果图 |
| **白盒测试** | 关注内部逻辑和代码路径 | 语句覆盖、分支覆盖、路径覆盖 |
| **灰盒测试** | 介于黑盒和白盒之间 | 接口测试 |

> 记忆要点：**等价类划分**和**边界值分析**是黑盒测试最常用的两种技术，高频考点。

### 4.4 测试覆盖率（白盒测试）

| 覆盖标准 | 要求 | 强度 |
|---------|------|------|
| **语句覆盖** | 每条语句至少执行一次 | 最弱 |
| **判定覆盖（分支覆盖）** | 每个判断的真假分支都执行 | 较弱 |
| **条件覆盖** | 每个条件的真假都取到 | 中等 |
| **路径覆盖** | 所有可能路径都执行 | 最强 |

> 记忆要点：覆盖强度从弱到强：**语句 < 判定 < 条件 < 路径**。

### 4.5 V模型

**V模型**将软件开发阶段与测试阶段一一对应，左侧是开发活动，右侧是对应的测试活动，形成"V"字形。

```
需求分析          ←→  验收测试（UAT）
  概要设计        ←→  集成测试
    详细设计      ←→  单元测试
      编码
```

| 开发阶段 | 对应测试阶段 | 测试重点 |
|---------|------------|---------|
| **需求分析** | 验收测试（UAT） | 验证系统是否满足用户业务需求 |
| **概要设计** | 集成测试 | 验证模块间接口和交互是否正确 |
| **详细设计** | 单元测试 | 验证单个模块/函数的逻辑是否正确 |

> 记忆口诀：**需求→验收，概要→集成，详细→单元**（从外到内，从粗到细）

## 五、数据工程

### 5.1 数据建模

数据建模的三个层次：

| 层次 | 模型 | 说明 |
|------|------|------|
| **概念模型** | E-R图（实体-关系图） | 描述业务概念，与技术无关 |
| **逻辑模型** | 关系模型（表结构） | 将概念模型转化为逻辑结构 |
| **物理模型** | 数据库表设计 | 具体的数据库实现 |

### 5.2 数据库设计范式

| 范式 | 要求 | 消除的问题 |
|------|------|---------|
| **第一范式（1NF）** | 每列不可再分（原子性） | 重复组 |
| **第二范式（2NF）** | 满足1NF + 非主键列完全依赖主键 | 部分依赖 |
| **第三范式（3NF）** | 满足2NF + 非主键列不传递依赖主键 | 传递依赖 |

> 记忆要点：**3NF是最常用的设计目标**，消除了部分依赖和传递依赖，平衡了数据冗余和查询性能。

### 5.3 数据仓库

**数据仓库**的四大特征：

| 特征 | 说明 |
|------|------|
| **面向主题** | 按业务主题组织（如：销售、客户），而非按应用系统 |
| **集成性** | 来自多个异构数据源，经过清洗整合 |
| **非易失性** | 数据一旦进入不轻易修改，保留历史数据 |
| **时变性** | 随时间变化，记录历史快照 |

> 记忆口诀：**主集非时**（面向主题、集成性、非易失性、时变性）

## 六、系统集成

### 6.1 系统集成的层次

| 集成层次 | 说明 |
|---------|------|
| **数据集成** | 通过共享数据库或数据交换实现集成 |
| **功能集成** | 通过API调用实现功能共享 |
| **界面集成** | 通过统一门户整合多个系统的界面 |
| **流程集成** | 通过工作流引擎整合跨系统业务流程 |

### 6.2 中间件

**中间件**是位于操作系统和应用软件之间的软件层，提供通用服务，屏蔽底层差异。

常见中间件类型：

| 类型 | 说明 | 示例 |
|------|------|------|
| **消息中间件（MQ）** | 异步消息传递，解耦系统 | RabbitMQ、Kafka |
| **交易中间件** | 保障分布式事务的一致性 | Tuxedo |
| **应用服务器** | 提供Web应用运行环境 | Tomcat、WebLogic |
| **数据库中间件** | 数据库访问和管理 | JDBC、MyBatis |

### 6.3 企业服务总线（ESB）

**ESB（Enterprise Service Bus）**是企业集成的核心基础设施，提供：
- 服务路由和协议转换
- 消息格式转换
- 服务编排和流程管理
- 安全和监控

## 七、软件配置管理

### 7.1 配置管理基本概念

**软件配置管理（SCM）**是对软件开发过程中产生的所有工作产品进行标识、控制、审计和报告的活动。

**配置项**：纳入配置管理的工作产品，包括：源代码、文档、测试用例、构建脚本等。

**基线**：经过正式评审和批准的配置项集合，是后续变更的基准。

| 基线类型 | 建立时机 |
|---------|---------|
| **功能基线** | 需求评审通过后 |
| **分配基线** | 概要设计评审通过后 |
| **产品基线** | 系统测试通过后 |

> 记忆口诀：**功分产**（功能基线→分配基线→产品基线），对应需求→设计→测试三个里程碑。

### 7.2 版本控制

**版本控制**是配置管理的核心工具，管理配置项的变更历史。

| 概念 | 说明 |
|------|------|
| **版本** | 配置项在某一时刻的状态 |
| **分支** | 从主线分出的独立开发线 |
| **合并** | 将分支的变更合并回主线 |
| **标签（Tag）** | 标记特定版本（如发布版本） |

### 7.3 变更控制

配置管理中的变更控制流程：

**提出变更申请 → 变更评估 → 变更审批 → 实施变更 → 验证变更 → 关闭变更**

> 记忆要点：变更必须经过**正式审批**才能实施，未经审批的变更是配置管理的大忌。

## 八、信息系统项目监理

信息系统项目监理是指由具备相应资质的监理单位，受建设单位委托，依据合同对信息系统工程建设进行监督和管理的活动。监理的职责可以概括为"**三控两管一协调**"：

**三控**是指质量控制、进度控制和投资（费用）控制，这是监理工作的核心目标。**两管**是指合同管理和信息管理，确保项目在合同约束下有序推进，并保持信息的准确传递。**一协调**是指组织协调，协调建设单位、承建单位及其他相关方之间的关系。

监理单位的定位是辅助建设单位管理项目，而非替代建设单位行使职权。监理单位与承建单位必须保持独立，不能是同一家公司，以避免利益冲突。

> 记忆口诀：**三控两管一协调**——质量/进度/投资控制，合同/信息管理，组织协调。

## 九、软件规模估算方法

软件项目估算是项目规划的重要环节，常用的估算方法各有侧重，精度和适用场景不同。

| 估算方法 | 特点 | 精度 | 速度 | 适用场景 |
|------|------|------|------|---------|
| **专家判断** | 依赖专家经验，最主观 | 低 | 快 | 早期粗估 |
| **类比估算** | 参考历史相似项目 | 低-中 | 快 | 早期，有历史数据 |
| **参数估算** | 统计关系+算法（如功能点） | 中 | 中 | 有历史数据和参数模型 |
| **自下而上估算** | 逐项估算后汇总 | 高 | 慢 | 详细规划阶段 |
| **功能点（FP）** | 基于功能规模，与技术无关 | 中-高 | 中 | 各类软件 |
| **用例点（UCP）** | 基于用例数量和复杂度 | 中 | 中 | 面向对象/用例驱动开发 |

其中，**功能点法（FP）**是最常用的规模度量方法，通过统计输入、输出、查询、内部文件、外部接口五类功能来衡量软件规模，与具体实现技术无关，适用性广。**用例点法（UCP）**则是面向对象开发中常用的估算方法，基于用例的数量和复杂度进行计算。

> 记忆要点：精度从低到高：**专家判断 < 类比估算 < 参数估算 < 自下而上估算**。项目越早期，估算精度越低；越到详细规划阶段，精度越高。

## 十、高频考点汇总

1. **螺旋模型**：最大特点是**风险分析**，每次迭代都进行风险评估，适合大型高风险项目。
2. **RUP四阶段**：初始→细化→构建→移交，口诀"初细构移"。
3. **需求开发四步骤**：获取→分析→说明→验证，口诀"获分说验"。
4. **测试覆盖强度**：语句 < 判定 < 条件 < 路径，路径覆盖最强。
5. **黑盒测试技术**：等价类划分、边界值分析（最常用）。
6. **V模型对应关系**：需求分析→验收测试，概要设计→集成测试，详细设计→单元测试。
7. **数据仓库四特征**：面向主题、集成性、非易失性、时变性，口诀"主集非时"。
8. **三条基线**：功能基线（需求后）→分配基线（设计后）→产品基线（测试后），口诀"功分产"。
9. **3NF**：消除部分依赖和传递依赖，是数据库设计的常用目标。
10. **监理三控两管一协调**：质量/进度/投资控制，合同/信息管理，组织协调；监理单位与承建单位必须独立。
11. **软件估算精度**：专家判断 < 类比估算 < 参数估算 < 自下而上估算；功能点法与技术无关，适用性广。

## 十一、易错点

- ❌ 螺旋模型适合需求明确的小型项目 → ✅ 螺旋模型适合**大型高风险**项目，核心是风险分析
- ❌ 白盒测试中语句覆盖最强 → ✅ **路径覆盖**最强，语句覆盖最弱
- ❌ 黑盒测试需要了解代码内部结构 → ✅ 黑盒测试**不需要**了解内部结构，只关注输入输出
- ❌ 数据仓库的数据可以随时修改 → ✅ 数据仓库具有**非易失性**，数据一旦进入不轻易修改
- ❌ 基线建立后不能变更 → ✅ 基线可以变更，但必须经过**正式的变更控制流程**
- ❌ 功能基线在系统测试后建立 → ✅ 功能基线在**需求评审通过后**建立，产品基线才是测试后
- ❌ 监理单位可以与承建单位是同一家公司 → ✅ 监理单位与承建单位必须**独立**，不能存在利益关联
- ❌ 自下而上估算速度快但精度低 → ✅ 自下而上估算精度**最高**，但耗时最长，适合详细规划阶段
- ❌ 概要设计对应单元测试 → ✅ 概要设计对应**集成测试**，详细设计才对应单元测试
- ❌ V模型支持迭代开发 → ✅ V模型是线性模型，**不支持迭代**，这是其主要缺点

**第 1 题** 以下关于软件开发模型的说法，正确的是？

A. 螺旋模型的核心特点是顺序执行，文档完整，适合需求明确的大型项目
B. 瀑布模型最大的优点是能快速响应需求变化，适合需求不稳定的项目
C. 螺旋模型将迭代开发与风险分析相结合，每次迭代都进行风险评估，适合大型高风险项目 ✅
D. 原型模型适合需求明确、规模较大的项目，因为可以快速构建完整系统

**解析**：螺旋模型=迭代+风险分析，适合大型高风险项目，C正确。A描述的是瀑布模型。B错：瀑布模型不能快速响应变化。D错：原型模型适合需求**不明确**的场景。

D. 路径覆盖 ✅

**解析**："覆盖所有可能的执行路径"= 路径覆盖，是白盒测试覆盖标准中最强的。语句<判定<条件<路径。

**第 3 题** 以下关于黑盒测试技术的说法，正确的是？

A. 等价类划分是将程序的所有输入数据划分为若干等价类，从每个等价类中选取代表性数据进行测试 ✅
B. 边界值分析是测试程序内部逻辑路径的技术，需要了解代码结构
C. 黑盒测试需要了解程序的内部逻辑结构，才能设计有效的测试用例
D. 路径覆盖是黑盒测试中最常用的覆盖标准

**解析**：等价类划分定义正确，A正确。B错：边界值分析是黑盒技术，不需要了解代码。C错：黑盒测试不需要了解内部逻辑。D错：路径覆盖是白盒测试标准。

**第 4 题** 以下关于数据仓库特征的说法，错误的是？

A. 数据仓库是面向主题的，按业务主题组织数据
B. 数据仓库具有集成性，来自多个异构数据源，经过清洗整合
C. 数据仓库中的数据可以随时修改和删除，以保持数据的最新状态 ✅（错误项）
D. 数据仓库具有时变性，随时间变化记录历史快照

**解析**：数据仓库具有**非易失性**，数据一旦进入不轻易修改，C的说法错误，故选C。

**第 5 题** 某软件项目完成了系统需求规格说明书的评审并获得正式批准。此时应该建立哪条基线？

A. 产品基线，因为需求是产品的基础
B. 分配基线，因为需求已经分配给各个模块
C. 功能基线，因为需求评审通过后建立功能基线 ✅
D. 设计基线，因为需求是设计的输入

**解析**：功能基线在需求评审通过后建立；分配基线在概要设计后；产品基线在系统测试后。口诀"功分产"。

**第 6 题** 某大型ERP项目规模大、技术复杂、需求不确定，且一旦失败损失巨大，项目经理希望每阶段都能识别和应对风险。最适合采用的开发模型是？

A. 瀑布模型，因为文档完整，过程清晰，便于管理
B. 敏捷模型，因为响应变化快，适合需求不确定的项目
C. 螺旋模型，因为将迭代与风险分析结合，适合大型高风险项目 ✅
D. 增量模型，因为可以分批交付，降低风险

**解析**：大型+高风险+每阶段识别风险 = 螺旋模型。敏捷适合小团队，增量侧重分批交付而非风险管理，C正确。
