## 一、立项管理（大纲第3章）

### 1.1 立项管理的内容

立项管理是项目正式启动前的准备阶段，核心任务是论证项目是否值得做。

**立项管理的主要工作**：
- 提出项目建议书（Project Proposal）
- 开展可行性研究
- 项目评估与论证
- 获得项目批准

### 1.2 可行性研究

**可行性研究**：在项目投资决策前，对项目的技术、经济、社会等方面进行全面分析，判断项目是否可行。

**两个阶段**：

| 阶段 | 说明 | 精度 |
|------|------|------|
| **初步可行性研究** | 粗略评估，判断是否值得深入研究 | 误差 ±20% |
| **详细可行性研究** | 全面深入分析，作为投资决策依据 | 误差 ±10% |

**可行性研究的四个维度**（高频考点）：

| 维度 | 核心问题 | 关键内容 |
|------|------|------|
| **技术可行性** | 技术上能否实现？ | 技术成熟度、技术风险、人员能力 |
| **经济可行性** | 经济上是否合算？ | 成本效益分析、投资回收期、NPV/IRR |
| **社会可行性** | 社会环境是否支持？ | 法律法规、政策环境、社会影响 |
| **风险可行性** | 风险是否可接受？ | 主要风险识别、风险应对策略 |

> 记忆口诀：**技经社风**（技术、经济、社会、风险）

**可行性研究报告的主要内容**：
1. 项目概述（背景、目标、范围）
2. 现状分析（现有系统/业务现状）
3. 需求分析（功能需求、性能需求）
4. 技术方案（系统架构、技术选型）
5. 经济分析（投资估算、效益分析）
6. 风险分析（主要风险及应对）
7. 结论与建议

### 1.3 项目评估与论证

**项目评估**：由第三方（评估机构）对可行性研究报告进行独立审查，确保其客观性和准确性。

**项目论证**：组织专家对项目的必要性、可行性和合理性进行综合评审。

> 区分：可行性研究是**项目方自己做**，项目评估是**第三方来审**。

**评估的主要内容**：
- 项目建设的必要性
- 技术方案的合理性
- 经济效益的可靠性
- 风险分析的充分性

## 二、配置管理（大纲第14章）

### 2.1 配置管理基础

**配置管理（CM）**：对项目生命周期中产生的所有配置项进行标识、控制、状态报告和审计的系统化活动。

**配置项（CI，Configuration Item）**：纳入配置管理的任何工作产品，包括：
- 源代码文件
- 需求文档、设计文档
- 测试用例
- 项目计划
- 可执行程序

**基线（Baseline）**：经过正式审查和批准的配置项集合，作为后续开发的基础，**只能通过正式变更控制流程修改**。

常见基线类型：
- **功能基线**：系统需求规格说明书通过评审后建立
- **分配基线**：软件需求规格说明书通过评审后建立
- **产品基线**：软件产品完成验收测试后建立

### 2.2 配置管理的5个活动（高频考点）

| 活动 | 说明 |
|------|------|
| **配置识别** | 确定哪些工作产品需要纳入配置管理，为其分配唯一标识符 |
| **配置控制** | 管理配置项的变更，确保所有变更都经过审批 |
| **配置状态报告** | 记录和报告配置项的当前状态和变更历史 |
| **配置审计** | 验证配置项是否符合要求，确保基线的完整性 |
| **发布管理** | 管理配置项的发布和交付 |

> 记忆口诀：**识控报审发**（识别、控制、报告、审计、发布）

### 2.3 配置管理数据库（CMDB）

**CMDB**：存储所有配置项及其关系的数据库，是配置管理的核心工具。

CMDB的作用：
- 记录所有IT资产和配置项
- 追踪配置项之间的依赖关系
- 支持变更影响分析
- 支持事件和问题管理

### 2.4 版本控制

版本控制是配置管理的重要组成部分：
- **版本号规则**：主版本号.次版本号.修订号（如 V2.1.3）
- **分支管理**：主干（main）、开发分支（dev）、发布分支（release）
- **常用工具**：Git、SVN

## 三、变更管理（大纲第15章）

### 3.1 变更管理概述

**变更管理**：对项目范围、进度、成本、质量等基准的任何修改进行系统化管理的过程。

**变更的来源**：
- 客户需求变化
- 技术问题导致的设计变更
- 外部环境变化（法规、市场）
- 项目执行中发现的问题

### 3.2 变更管理的角色职责（高频考点）

| 角色 | 职责 |
|------|------|
| **变更申请人** | 提出变更请求，说明变更原因和预期效果 |
| **变更经理（项目经理）** | 评估变更影响，组织CCB审批 |
| **CCB（变更控制委员会）** | 审批或拒绝变更请求，是变更决策的最高权力机构 |
| **配置管理员** | 执行已批准的变更，更新配置项和基线 |

> 铁律：**任何变更必须经过CCB审批**，项目经理无权单独批准变更（除非CCB授权）

### 3.3 变更管理工作程序（高频考点）

```
变更申请 → 变更评估 → CCB审批 → 变更实施 → 变更验证 → 变更关闭
```

详细步骤：

1. **提出变更请求**：填写变更申请单，说明变更内容、原因、影响范围
2. **变更影响评估**：项目经理分析变更对范围/进度/成本/质量/风险的影响
3. **CCB审批**：CCB根据评估结果决定批准、拒绝或推迟
4. **变更实施**：按批准的方案执行变更，更新项目计划和基线
5. **变更验证**：确认变更已正确实施，达到预期效果
6. **变更关闭**：更新变更日志，归档变更记录

### 3.4 变更与其他管理要素的关系

变更对各知识域的影响：

| 影响领域 | 变更影响 |
|------|------|
| **范围** | 范围变更是最常见的变更类型，需更新WBS和范围基准 |
| **进度** | 范围增加通常导致进度延迟，需重新制定进度计划 |
| **成本** | 范围或进度变更通常导致成本增加，需更新成本基准 |
| **质量** | 变更可能引入新的质量风险，需更新质量计划 |
| **风险** | 变更可能带来新风险，需重新进行风险识别 |

> 关键原则：**变更是不可避免的，但必须受控**。未经批准的变更（镀金/Gold Plating）是严格禁止的。

### 3.5 镀金（Gold Plating）

**镀金**：项目团队在未获得客户要求或批准的情况下，自行添加额外功能或超出范围的工作。

- 镀金是**不良行为**，会导致范围蔓延、成本超支、进度延误
- 项目经理应严格控制范围，防止镀金

---

## 四、高频考点汇总

1. **可行性研究四维度**：技术、经济、社会、风险（技经社风）
2. **初步可行性 vs 详细可行性**：精度不同，初步±20%，详细±10%
3. **配置管理5活动**：识别→控制→报告→审计→发布
4. **基线**：经正式审批的配置项集合，只能通过变更控制修改
5. **变更管理流程**：申请→评估→CCB审批→实施→验证→关闭
6. **CCB是变更决策最高权力机构**，项目经理不能单独批准变更
7. **镀金是禁止的**，任何额外工作都需要正式变更申请

---

## 五、易错点

- ❌ 项目经理可以自行批准变更 → ✅ 变更必须经过**CCB审批**
- ❌ 可行性研究只看技术和经济 → ✅ 还要看**社会可行性和风险可行性**
- ❌ 基线可以随时修改 → ✅ 基线只能通过**正式变更控制流程**修改
- ❌ 配置管理只管代码 → ✅ 配置管理管所有**工作产品**（文档、代码、测试用例等）
- ❌ 镀金是对客户负责的表现 → ✅ 镀金是**不良行为**，会导致范围蔓延
